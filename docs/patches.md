**Five patches were retired between v0.15.1 and v0.20.1** because upstream shipped the same fix natively (superseding, sometimes with a strictly better version): `auxiliary-client-gpt5-max-completion-tokens` (v0.15.1 — upstream omits `max_tokens` by default for non-Anthropic custom endpoints), `slack-audio-mime-ext` (v0.18.2 — upstream's own `_resolve_slack_audio_ext()` maps MIME→extension more thoroughly, `.m4a` fallback not `.ogg`), the `_resolve_thread_ts` synthetic-thread guard hunk (v0.19.0, with the switch to `reply_in_thread: true` — it was already dead code and would have become actively harmful under threads), `auxiliary-client-anthropic-mode-respect` and `scheduler-skip-resolver-for-slack-ids` (both v0.20.1 — upstream's `wrap_base` and `resolve_send_target()` are supersets of what these patches did). Full per-patch reasoning: `git log --oneline -- patches/` and the retirement commits themselves; the transferable lesson (check "is this now upstream's job" before rewriting a failing patch) lives in `.claude/skills/hermes-update/SKILL.md`.

> **Slack threading = context-window boundary (changed at v0.19.0).** `slack.reply_in_thread` is now **`true`** (upstream's default — every read site is `.get("reply_in_thread", True)`; the key is absent from `DEFAULT_CONFIG`, so the code default governs). This is not cosmetic: `build_session_key()` (`gateway/session.py:1029`, key assembly at `1114-1131`) appends `thread_ts` to the session key **only when `source.thread_id` is set**, and the inbound scoping block (`adapter.py:5607-5638`) sets `thread_id` to the message's own ts for top-level messages *only* when `reply_in_thread` is true. So: **one Slack thread == one session == one context window.** Under the previous `false`, every top-level channel message collapsed into a single never-resetting session (`agent:main:slack:group:<team>:<C…>:<U…>`) — observed live at 213 messages over 6 days — while a real thread reply got an isolated window, with no visual cue which one you were in. Consequence of the flip: continuing a topic means replying **inside** its thread; a new top-level message is deliberately a clean slate. `session_reset.mode` is unset (default `none`), so only the compressor bounds a long-lived thread. Note `group_sessions_per_user` only affects the *flat* key shape — `isolate_user` is forced off whenever a thread is present (`session.py:1126-1129`).

> **Platform architecture rewrite (v0.18.x).** Upstream moved built-in chat platforms out of `gateway/platforms/` into a plugin system: Slack now lives at `plugins/platforms/slack/adapter.py` (previously `gateway/platforms/slack.py`, which no longer exists). `gateway/platforms/base.py` (the shared response-delivery base class) stayed in place. All Slack-targeting patches below were rewritten against the new `adapter.py` path and file structure during the v0.16.0 → v0.18.2 update.

Two shapes, both observed live on 2026-09-15: a **stale gitlink** — a nested git repo is recorded in the per-project index as a mode-160000 gitlink while it is healthy, and macOS's `com.apple.tmp_cleaner` (daily, `-atime/-mtime/-ctime +3`) then removes that repo's `.git/HEAD`, `.git/config` and `.git/refs` while leaving `.git/objects` and `.git/index` behind, so the directory still reads as a nested-repo boundary git cannot resolve (`Schwerwiegend: 'wave-gate-test/.git' nicht als Git-Repository erkannt`, logged 02:18:40 and 02:18:57) — and a **file deleted mid-walk** — `git add -A` walks the tree and then reads each entry, so a file that disappears in between fails the whole add with `unable to stat '<path>': No such file or directory` (logged 12:35:10: Claude Code's own scratch under `/tmp/claude-501`, deleted as an episode ended; the identical add succeeds on the immediate retry, verified by reproducing the race against a 6000-file tree). The retry *is* the repair for the gitlink case — dropping it is a change against the ref tip, so `_index_unchanged_reason` does not skip, `write-tree` commits a gitlink-free tree and `update-ref` advances the tip, so no later read-tree can resurrect it. A persistent failure (a commitless nested repo: `error: 'nested/' does not have a commit checked out`, whose stderr carries **no** `.git` token) still fails the retry and is reported once, from the retry's own stderr. `--ignore-errors` does not help (rc=1 with the index half-populated) and neither does `info/exclude` for a gitlink (already in the index). **Three constraints that are easy to get wrong:** (1) the stderr test must be locale-independent — git localizes the message (`Schwerwiegend: …` under this host's de_DE locale), so matching the English sentence silently never fires here; the patch tests for a `.git` token instead. (2) The health probe must be filesystem-only — `<path>/.git/HEAD` existence, with `.git` as a **file** (submodule checkout) always counted live. Any `git -C <path> rev-parse` under `_git_env` answers about the store (rc=0 even on a dead nested repo), so it would classify every broken gitlink as healthy. (3) The probe must be `.git/HEAD` existence, not `rev-parse --verify HEAD`: a nested repo with no commits is valid but has no HEAD commit, and treating it as dead would force-remove a live gitlink and then fail the retry anyway. **Defect 2 — a path stays tracked after its pattern reaches `DEFAULT_EXCLUDES`.** `info/exclude` was written **once, at store init**, and `git add -A` honours it only for paths that are *not yet* in the index — so a path committed before its pattern existed kept being staged on every snapshot, and the live store still carried the pre-`claude-501/` list.
